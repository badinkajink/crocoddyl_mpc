The matrix-free Delassus, measured inside a crocoddyl MPC

Session 14. The S13 controller works and is twice too slow: a 50-node warm-started BoxFDDP step costs 39.5 ms against a 20 ms control period. Sathya et al.'s matrix-free Delassus operator is the obvious thing to try, because unlike MuJoCo — where the default solver never forms a Delassus matrix at all — crocoddyl's contact forward dynamics builds one at every node of every iteration. This page reaches into Pinocchio's C++-only implementation, checks it, times it against the operator it would replace, and answers whether it belongs in this loop.

crocoddyl 3.2.1, Pinocchio 4.1.0, conda-forge, one 28-core x86-64 box. Operator timings are best-of-300 in microseconds; MPC step times are means, because there the question is what a control period costs in practice. Everything below is regenerated from runs/2026-08-06_session14/delassus.json by lean_analysis/croco_delassus_page.py.

The short version. The operator is exact here — 6.7e-16 relative error against an independently assembled J M⁻¹Jᵀ, holding to 6.7e-16 out to 978 constraint rows. It is also genuinely cheaper to set up than the explicit build, by 1.7× at this robot's braced contact set. And it is still the wrong tool for this loop, for two independent reasons that both had to be measured: the Delassus is 2.3% of a node, and crocoddyl's access pattern — materialise the inverse once, then GEMM — is precisely the pattern a matrix-free operator loses. Dropped in at the only place it fits, it is 5.0× slower.

1. Why this is worth asking here and was not worth asking in MuJoCo

The companion study (~/mujoco/mfdelassus) ported the paper's operators into MuJoCo and found the headline result did not transfer, for a structural reason: MuJoCo's default Newton solver is primal. It works in the nv-dimensional acceleration space and never assembles efc_AR = J M⁻¹Jᵀ + R at all. The paper's object was absent from the hot path.

crocoddyl is the opposite case. Every node of the S13 problem is a DifferentialActionModelContactFwdDynamics, and it builds the Delassus matrix twice per node per iteration:

calc      pinocchio::forwardDynamics(model, data, tau, J, a0, mu)
              cholesky::decompose(M)                 -> U, D
              sDUiJt = D^-1/2 U^-1 Jᵀ
              data.JMinvJt = sDUiJtᵀ sDUiJt + mu I   <- THE DELASSUS MATRIX
              data.llt_JMinvJt.compute(JMinvJt)      <- and its Cholesky
              lambda_c = llt.solve(-J M^-1 (tau-nle) - a0)

calcDiff  pinocchio::getKKTContactDynamicMatrixInverse(model, data, J, Kinv)
              bottomRight = -G^-1        (nc solves against the factor from calc)
              topLeft     = M^-1         (nv sparse Cholesky solves)
              three GEMMs assembling the Schur complement into Kinv

So the object exists, it is regularised exactly the way the paper's damped operator is (INV_DAMPING = 1e-4, which S13 needs anyway because two 6D feet plus three brace points on a 33-DOF robot is a redundant, singular constraint set), and it is rebuilt 50 times per control step. That is a real target.

The caveat that made this page necessary. Pinocchio 4.1.0 ships the matrix-free operator as DelassusOperatorRigidBodySystemsTpl in src/algorithm/delassus-operator-rigid-body.hxx and does not expose it to Python — only the Dense, Sparse and CholeskyExpression variants are wrapped. The MuJoCo study therefore had to quote the paper's own timings for it. Everything below is measured.

2. Getting at the operator

No submodule and no rebuild of Pinocchio was needed. The operator is header-only, so a single translation unit compiled against the conda prefix reaches it, and linking -lpinocchio_default -leigenpy puts it in the same typeinfo registry as the Pinocchio pywrap — which is what lets bp::extract<pin::Model&> succeed on a Python pin.Model. Two things had to be right or nothing compiles:

  • #include <pinocchio/fwd.hpp> before boost/python.hpp, and the four definitions from pinocchioTargets.cmake verbatim (BOOST_MPL_LIMIT_LIST_SIZE=30, BOOST_MPL_LIMIT_VECTOR_SIZE=30, BOOST_MPL_CFG_NO_PREPROCESSED_HEADERS, BOOST_FUSION_INVOKE_MAX_ARITY=12). The constraint collection is a boost::variant over 25 types dispatched through 8-argument boost::fusion::invoke; at boost's defaults of 20 and 6 the header stack does not instantiate.
  • applyOnTheRight is declared for a general matrix argument but only instantiates for a vector — the matrix path calls a vector-only Eigen method inside mapConstraintForcesToJointSpace. G has to be materialised column by column.

The result is lean_analysis/croco_ext/mfdelassus.cpp, which also exposes the operator as a reusable Python class, closing the caveat above for anything downstream:

import croco_mfd
pin.computeJointJacobians(model, data, q)          # the operator's precondition
op = croco_mfd.DelassusMF(model, data, constraint_models, damping=1e-4)
op.compute()                                       # or compute(False, True) for solves only
y = op.apply(x)                                    # G x
z = op.solve(x)                                    # (G + mu I)^-1 x

This is the paper's Fig. 3 claim, reproduced on the H1-2 rather than cited: the forward operator agrees with the assembled matrix to machine precision. Nothing below is a question about correctness.

4. How much of the MPC step is Delassus at all?

Before optimising an operator it is worth knowing what fraction of the node it is. The S13 action models are ablated by rebuilding each DifferentialActionModelContactFwdDynamics with an empty CostModelSum and the same contacts, actuation and damping — so the difference is exactly what the cost stack adds on top of a shared kinematics pass.

Two things in that table decide the rest of the page.

The Delassus is 8.0 µs, which is 34% of the two calls and 2.3% of the node. Not nothing — it is the largest single item inside calc — but the node is dominated by things a Delassus operator cannot touch.

Almost all of calcDiff's KKT cost is not Delassus. This is the part that is easy to get wrong from reading the call graph. getKKTContactDynamicMatrixInverse looks like a Delassus operation and costs 16.5 µs, the biggest item in the dynamics; but it does not refactorise anything. It reuses data.llt_JMinvJt computed back in calc, and spends its time on M⁻¹ as a dense nv×nv block (8.6 µs, 33 sparse Cholesky solves) and three Schur GEMMs (6.2 µs). The only Delassus work left in calcDiff is one nc-column triangular solve, 2.0 µs.

5. The operator against the build it would replace

Both sides run on the same Pinocchio constraint models (crocoddyl's ContactModel6D at a sole is a FrameAnchorConstraintModel; its ContactModel3D at a brace site is a PointContactConstraintModel), at the same configuration, with the same 1e-4 damping, in the same process. The explicit side is not Pinocchio's fastest — it is crocoddyl's own sDUiJt/JMinvJt algorithm, because the question is what the operator would displace. Both exclude the shared computeJointJacobians.

This is the paper's result, holding: setup is 1.7× cheaper matrix-free at nc=21 (4.01 µs against 7.09 µs), because the explicit route pays O(nc²nv) to form G and O(nc³) to factorise it while the operator pays one O(nv) pass over the augmented articulated inertias. Our numbers also sit alongside the paper's Table I for the G1 at comparable size (nv=35, m=24: explicit 9.37/13.94 µs, matrix-free 3.66/3.96 µs), which is a useful cross-check that the harness is measuring the right thing.

And this is why it does not help here: each application is 2.4× more expensive (0.74 µs against 0.32 µs), because the explicit route amortises — once you have paid for a Cholesky factor, every further right-hand side is a pair of triangular solves. Break-even is 7 applications. crocoddyl asks for 22 per node: one in calc for the contact forces, and nc more in calcDiff for the −G⁻¹ block. Past break-even, the factorisation wins.

6. The drop-in, done and measured

The above is an argument from operation counts, and arguments from operation counts are worth exactly as much as the measurement that follows them. So the replacement was built at the only place it fits. What crocoddyl's calcDiff needs from the contact dynamics is one object applied to a set of right-hand sides:

a_partial_dtau = M⁻¹ − M⁻¹Jᵀ G⁻¹ J M⁻¹,     G = J M⁻¹Jᵀ + mu I

Fx = a_partial_dtau (dtau_dx − [dtau_dq | dtau_dv]) − a_partial_da · da0_dx     2·nv = 66 columns
Fu = a_partial_dtau · dtau_du                                                        nu = 27 columns

Route A is crocoddyl's: materialise a_partial_dtau densely, then one GEMM. Route B is the matrix-free replacement, which cannot materialise anything — its premise is that you apply G⁻¹ to vectors — so it has to invert the order and run one KKT solve per right-hand-side column. Route B is given every advantage available: it reuses the same stacked Jacobian (an explicit object it arguably should not be allowed) and the same sparse LTDL factor of M, so the only difference between the routes is how G⁻¹ is obtained.

The two routes agree to 5e-11, so this is the same computation, and the matrix-free one is 1.8× to 5.0× slower. The ratio grows with the column count, which is the signature of the problem: crocoddyl amortises one factorisation over 93 right-hand sides, and an operator that refuses to factorise pays for all 93 separately.

This is not a defect in the operator. It is a mismatch between an operator designed for solvers that touch G a handful of times per configuration (ADMM, PGS, proximal contact solvers) and a DDP, which touches it 93 times per node because it wants derivatives, not forces. The same operator in an ADMM contact solve at the same nc would be ahead after 7 applications.

7. Where the verdict flips

Both routes were swept over constraint count by stacking extra point contacts on the brace frames, at the braced configuration. Past nc=21 this is synthetic — the H1-2 does not have 300 contact points — but the scaling is a property of nv and nc, not of where the contacts physically are. The crossover sits at nc ≈ 37 — a factor of 37/21 away from the lean problem, or roughly six more three-dimensional contact points than the brace has. The memory story is far more lopsided than the time story and matches the MuJoCo finding exactly: at 978 rows the operator needs 37 KB against 15 MB, 409× less, because its footprint is O(nv) and independent of the constraint count.

So there is a version of this problem where the operator is the right answer, and it is worth naming it, because the lean study could plausibly walk into it. Reformulating the 86 box keep-out costs as hard constraints rather than penalties would put 86 rows into the constraint set on its own; a whole-body contact-rich formulation (both hands, forearms, a torso lean against the table, feet with per-corner point contacts instead of 6D wrenches) reaches the same place. At nc = 138 the matrix-free route is already 2.9× ahead.

8. What this means for the 20 ms budget

The S13 MPC step measures 39.5 ms for H=50 at one iteration. Counting generously — calc twice per node for the rollout plus a line-search trial, calcDiff once, which raises the Delassus share from 2.3% to 3.8% of a braced node. That node share is itself an upper bound on the step share, because the Riccati backward pass contains no Delassus at all.

The Amdahl ceiling. If the Delassus cost went to zero — faster than any operator can be — the step goes from 39.5 ms to 38.1 ms. That is 1.5 ms against a 19.5 ms overrun. The measured matrix-free operator moves it the other way.

The loop needs a factor of two, and it is not hiding in the contact dynamics. It is in the cost stack: 72% of a braced node, 242 µs of calcDiff alone, and the 86 keep-out residuals are most of it. S13 already took the first 2.9× there by moving the keep-out activation into C++ (118.8 → 40.3 ms). The remaining candidates are the same kind of thing and none of them are Delassus:

  • Prune the keep-out set per node. 86 points × 50 nodes is 4300 residuals evaluated every control step, and at any given node almost all of them are far outside the barrier and contribute exactly zero. A per-node active set recomputed on the plan is the obvious 5–10×.
  • The actuation model is Python. ActuationModelJointPassive is a Python subclass of ActuationModelAbstract allocating a 33×66 array per call; it costs 5.7 µs in calcDiff and 2.3 µs in calc, ~8% of the dynamics, for arithmetic that is a diagonal.
  • Shorten the horizon rather than the node. The H=25 sweep in S13 measured 89 ms against 119 ms for H=50 at the same iteration count, and it did not fall over.

10. Bottom line

  • Pinocchio's matrix-free Delassus operator is now reachable from Python here (croco_ext/mfdelassus.cpp, class DelassusMF), which the MuJoCo study could not do — its numbers for the operator were the paper's, and these are measured.
  • It is exact — 6.7e-16 relative error against an independently assembled Delassus, from nc=12 to nc=978.
  • Its setup is 1.7× cheaper than crocoddyl's explicit build at this robot's braced contact set, and its memory is 409× smaller at scale. The paper's claims hold.
  • It still does not belong in this loop. crocoddyl amortises one Cholesky factor over 93 right-hand sides; break-even is 7 applications. Dropped in and verified to produce the same derivatives to 5e-11, it is 5.0× slower.
  • And it could not have helped much even if it had won. The Delassus is 2.3% of a node, 3.8% counting a line-search rollout; a free one saves 1.5 ms of a 39.5 ms step.
  • The crossover is nc ≈ 37. If the keep-out box ever becomes a hard constraint set, or the brace becomes contact-rich, this conclusion inverts — the machinery to re-run the measurement is in the repo.
