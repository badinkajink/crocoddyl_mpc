One twin run is not 260, and the two things worth building next

Session 19. What the first DDS deployment does and does not license, one experiment the corrected gripper makes possible, and plans for a return-to-stand controller and a live GUI.

Companion to the S18 assets page. Numbers here come from studies/runs/2026-08-17_session19/; the deployment code is croco/twin/lean_twin.py and studies/croco_twin.py at 086baa5.

1. No, and the gap is not small

The question was whether the twin run is effectively equivalent to the testing that came before it, and therefore whether sim2real is next. It is not, and the honest way to see why is to put the two side by side.

What the twin run does license is narrow and real: the command tuple means the same thing on both sides of the wire, the 27-motor order is right end to end, the loop holds its period, and the maneuver survives a real clock with real dead time. That is the plumbing, and the plumbing now works. It is one cell of one grid with a perfect estimator, which is not evidence about the robot.

The single biggest gap is the base pose. rt/lowstate carries IMU and encoders and nothing else, so the twin run reads the true base off rt/sim_state. Every S18 number was taken with a per-run bias plus white noise standing in for an estimator; the twin run was taken with that error set to exactly zero. The repo’s own rule — ground truth is never on by default — exists because a controller that reads it works in sim and fails on hardware. Until a real estimator is in this loop, the twin result is strictly easier than the replay it is being compared to.

What would close it

The work is mechanical, not novel, and that is the point: croco_twin.py takes the same --dir and --tag the grid does. Running the S18 grid through the twin is a loop around the script that already exists. At roughly 30 s of build plus 4 s of run per cell, 260 runs is about three hours of wall time, and the comparison it produces — survival per cell over DDS versus in process — is the first thing that could honestly be called equivalent.

One thing had to be fixed before spending those three hours, or the run would have measured the harness instead of the controller. It is fixed — and it turned out not to be the thing it looked like.

2. RESOLVED: the watchdog, which was two bugs wearing one number

Written first as “62 of 195 periods fly blind”. Both halves of that turned out to be wrong, in opposite directions, and the correction is more interesting than the original claim.

The 62 was a label, not an event

The loop logs phase on every row, and phase is a field on the loop rather than a property of the period. A stale state set it to safe — and nothing ever set it back, because with no bring-up requested _phase_command returns early without touching it. Every period after the first trip was solved, clamped, commanded and logged exactly as normal, and labelled safe anyway.

Separating the rows that actually took the watchdog branch (they carry no solve_ms, having never reached the solver) from the rows that merely inherited the label gives 1 real trip and 61 mislabelled periods. The run was never blind a third of the time. ControlLoop now resets the phase each period and counts watchdog_trips directly, so the claim is read off a counter instead of inferred from a histogram.

The GIL was real, and worse than a callback thread being slow

The underlying mechanism held up. Measured directly: a Python thread ticking at 1 ms, and a 112 ms crocoddyl solve on the main thread.

largest gap in the ticker
idle baseline1.25 ms
during solver.solve()112.81 ms

Boost.Python releases the GIL nowhere, so the solve stops every other Python thread in the process for its full duration. unitree_sdk2py's receive path is two Python hops — a cyclonedds listener invoking a Python callback, which hands the sample to a Python queue thread — and neither can run while the solver is in C++. It presents as a network problem and is not one: cyclonedds’s own receive threads are C and were never blocked. Only the Python draining them was.

The fix was the receive strategy, not the GIL

Releasing the GIL around the solve was the obvious repair and it is the expensive one — a Boost.Python shim linking crocoddyl, and a standing constraint that no action model in the problem may ever be Python-derived. Inverting the receive is neither. The reader accumulates in C; the control thread, which by definition holds the GIL at the moment it wants a state, takes the newest sample itself. No second thread, no queue, nothing to starve. PollingReceiver in croco/plant/dds_plant.py, about forty lines, and it is now the default.

The p95 is the line to read. On the callback path one control period in twenty planned from a state a full solve out of date — 16 ms of dead reckoning that the latency compensator was already predicting forward from, and therefore double-counting. The tail reached 48 ms against a 50 ms threshold, which is why a single 65 ms sample was enough to trip it on the earlier run.

One honest caveat about what age now means. Polling stamps the state when this thread takes it, so within a period there is no staleness left to measure — 0.006 ms is not a transport time, it is the cost of calling monotonic() twice. The watchdog still works, and now catches the failure it was always meant to: nothing new to take means the stamp stops advancing and the age grows. Sub-period transport delay is simply no longer visible there, so the plant counts samples per poll instead. Measured 0.98 — which incidentally confirms the reader’s history is KeepLast(1), so the sample taken is by construction the newest published, and there is no queue that can fall behind.

3. RESOLVED: wrist roll works, and it is not why the palm is empty

The exploration as posed: with the corrected gripper, can wrist roll drive the palm down into the table and reproduce a palm brace? Answer: yes, 8° of it, in every cell. But the sweep found the reason the planner never does it, and it is not a reachability problem.

The measurement

Swept at the certified pose q*, across all 26 S18 cells, one wrist joint at a time. Lowest-point computed from the collision primitives directly — mj_geomDistance returns spurious exact zeros on these box/cylinder pairs and briefly made wrist yaw look like the answer, when in fact the yaw axis is vertical at this pose and yaw moves the gripper neither down nor flat.

wrist roll+7.8°7.8°−10.2 mm140°26 / 26
wrist pitch+6.6°6.7°−11.5 mm18°26 / 26
wrist yawnever———0 / 26

So the intuition was geometrically right and the axis was right. What it was not was an alignment fix: the palm face is already 0.05–0.07° from flat in all 26 cells. It is not edge-on and never was. It is 9.0 mm too high — to within 0.1 mm, in every cell, because that height is set by wrist-link geometry and not by the target. Rolling to land it costs 8° of tilt rather than removing any, which is still far inside a μ = 0.6 cone (31°), and presses the wrist pad 10 mm deeper — so a palm brace is coupled to the wrist brace, not a second independent support.

Why the planner never does it

resolved_contacts was fabricating the contact. When the narrowphase reports nothing for a brace body it falls back to the SITE point with an assumed vertical normal. The narrowphase reports nothing for the gripper in 26 of 26 cells. So the static QP certified force balance at a point hanging 22 mm in the air, the OCP anchored its palm contact there, and the plan satisfied it to 0.88 mm. Nothing in the objective ever asked the gripper to descend, because by the model’s own accounting it was already exactly where the contact was. The “19 of 26 cells admit a palm contact” result has to be read that way: it certified a force at a point near the gripper, not a contact.

The fallback now announces itself, once per site, with the height. It stays a fallback rather than becoming an error because the feet legitimately use it — a flat floor with a deliberate four-point corner model of a sole is an approximation, not a missing contact.

And the force accounting was open

f_brace was keyed on the plan’s subset, so a robot–table contact on any body that no site names was summed nowhere. What actually carries the brace is left_wrist_pad, which lives on left_wrist_yaw_link. Re-running the cell with the accounting closed: 177.6 N elbow, 0.0 N palm, and 5.2 N braced-mean / 59.3 N peak that had previously been reported nowhere at all — across left_elbow_link, left_wrist_yaw_link, and unexpectedly right_magpie_gripper. Every replay now carries an F_other column and names the bodies in it.

What this makes the palm question

Not “can the palm reach the table” — it can, from every cell, with a joint that has 140° to spare. The question is whether a brace whose two contacts share the same 10 mm of wrist compression is worth having, and that is answerable only after the contact is placed on the surface instead of above it. That is a change to resolved_contacts, a re-certification, and a re-plan — a session, not a patch, and the S18 grid would have to be redone with it.

4. RESOLVED (first pass): the release is not the dangerous part — the brace is

The plan above said: turn n_return on, expect the failure backward, and measure the support margin through the release. Done, on x1050_y-235_z1098_dy+000, elbow+palm, 60 return nodes (1.2 s) against the same cell at n_return: 0. The prediction was wrong, and usefully so.

Both plans converge and are feasible. The n_return: 0 control reproduces the S18 cell to twelve digits (cost 24.733003063938), so the comparison is clean.

The robot stands back up. The margin at the release is +41.5 mm and rises monotonically to +76 mm; it never dips. Traced through the transition, the brace goes from 185.7 N to 0.0 N in a single control period while the feet step from 460.5 N to 764.4 N — a 300 N transfer, peaking at 1.13× body weight, absorbed without the CoM leaving the support polygon. Contact removal really is the free transition, and the “expect failure backward” instinct simply does not show up in the data.

What the return phase actually costs is the brace. Braced-phase margin drops 61.2 → 28.6 mm, brace-entry penetration goes 0.5 → 7.9 mm, and the hand ends 88.8 mm off target instead of 5.3 mm. The mechanism is in the cost shaping, not the physics: with n_return > 0 the terminal node is no longer braced, so it drops the 10× reach weight and flips its state reference to x0. The brace stops being what the terminal node rewards, and the solver spends brace fidelity to buy a clean landing. The fix is to stop leaning on the terminal node — put a strong hold/reach cost on the LAST BRACED node, where it belongs, instead of getting it for free from a terminal that no longer exists.

What is still open here

  • Release rate. 60 nodes was one guess and it worked; the sweep over unloading duration is still the interesting variable and has not been run.
  • Settle window. The plan ends with terminal_vel_norm 1.75 rad/s against 0.035 for the braced terminal — the OCP hands over a robot that is still moving, and the MPC catches it. “Recovered” should mean still standing seconds later, which needs a settle window past the last node.
  • The handoff. Unchanged from the plan and now more clearly needed: the loop signs off with a damping stop when the policy retires, which is why the twin robot collapses five seconds after a successful run. With a return phase the maneuver ends in a stand, and holding that stand is a controller, not a None. It belongs in ControlLoop next to the bring-up phases it already owns.
  • The twin. Recovery over the wire has not been run. It is where deployment gets harder, not easier — though with the receive path fixed (§2) the state is now current at the moment the release needs it.

5. Plan: a live GUI, without the MJPC bloat

Not too ambitious, if the MVP is scoped to the three things actually wanted: watch the planner live, change cost weights live, plot costs. The first and third are display; the second is the one that could have been hard, and it is not.

Live weights are free. Verified against this environment: costs.costs["reg"].weight = 7.5 mutates in place on a built CostModelSum, and changeCostStatus switches a term off entirely. The OCP does not need rebuilding to retune it, which is what makes a slider meaningful rather than a restart button.

Where it taps in

ControlLoop already takes an on_step(row, state, cmd) callback and is already called once per control period with everything a display needs. That is the whole integration surface — the GUI is a consumer of a hook that exists, not a rewrite of the loop.

Browser, not a GL toolkit

MJPC’s GUI is GLFW plus ImGui compiled into the agent, and inheriting that is inheriting the bloat the request explicitly excludes. A small HTTP plus WebSocket server in the controller process, with a plain HTML page, wins on four counts: no GL dependency to fight, it works headless and over SSH, it composes with the twin already running in another process, and the plotting is a few dozen lines of canvas rather than an ImGui port. The cost is that the 3D view is not free the way it is in a native viewer.

For the 3D view, the MVP answer is to not build one: run mujoco.viewer.launch_passive in the twin process, which already exists and already shows the robot, and let the browser own the numbers and the sliders. Overlaying the predicted trajectory is the one thing worth adding on top — the MPC returns solver.xs every period, and drawing that horizon as a line in user_scn is what “watching the planner” actually means.

MVP, in the order it should be built

  • Telemetry out. on_step pushes solve time, phase, per-term cost, step length, saturation counts and state age over a WebSocket. Ship this alone first — it replaces the JSON-at-the-end workflow every run currently uses, and it is useful before any UI exists.
  • Plots in. Rolling traces of solve time against the period, cost per term, and support margin. The per-term breakdown is the one that pays: it is currently only visible by running croco_speed.py terms offline.
  • Weights back. Sliders posting to a queue the loop drains between periods — never mid-solve. Show the value and the default, and log every change into the run JSON, or a retuned run becomes unreproducible.
  • Horizon overlay in the passive viewer, from solver.xs.
  • Not in the MVP: editing the task, saving configurations, a scene tree, a built-in profiler. That is where MJPC’s GUI became something to maintain rather than something to use.
One hazard worth naming. A GUI that retunes weights live makes it easy to produce a run nobody can reproduce. Every weight change must land in the run artifact, and a run whose weights differ from the plan’s should say so in its summary — the same discipline that makes --base truth something you have to type.

6. Housekeeping: the media links

Every video in every docpage in this series was a broken element. The pages reference media/<name> relative to docs/lean/, and that directory did not survive the move out of the pre-rename checkout and the studies/ reorg. It was silent because a missing <video> renders as blank space rather than as an error.

docs/lean/fix_media.py resolves it: it scans every page for references, searches all four places media has lived, newest mtime wins, and copies what it finds. 33 of 46 restored. The directory is gitignored, so the script is the deliverable — on a fresh checkout fix_media.py --copy is what makes the pages viewable.

The remaining 13 exist nowhere on this machine. They are S13 and S14 replay videos, and they are not worth regenerating: both sessions predate the gripper correction, so re-rendering them would produce videos of a model this series has since established was 90° out. The script names them rather than leaving blank rectangles.

7. Where this leaves the list

Three of the four items above are done, and two of them changed what the fourth is worth doing to.

Two of these were reporting failures rather than engineering ones, and that is the pattern worth carrying forward. The watchdog number was a stale phase label. The palm force was a contact fabricated in mid-air by a silent fallback, certified by a QP that had no way to know, and reported against a body-keyed sum that dropped every contact it did not have a name for. In all three the physics was fine and the instrument was lying — so all three fixes are now instruments that say something when they cannot answer, rather than answering anyway.

What to do next, in order: the twin grid, which is mechanical and finally measures the controller rather than the harness; then the last-braced-node cost that §4 identified, which is a small change with a clear prediction; then the palm, which needs resolved_contacts to place contacts on surfaces and the grid redone behind it.

The GUI is still the odd one out, and still the right thing to build while a three-hour grid is running: nothing above depends on it, and every finding on this page would have been quicker to see with a live plot of costs and contact forces than with a print statement.
