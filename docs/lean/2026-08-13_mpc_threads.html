Multithreading the crocoddyl MPC: one of three stages is parallel

Session 16, a companion to S15. That page left the controller real-time on the mean and not on the tail, and named threading as the obvious next lever: ShootingProblem.nthreads exists, the conda-forge crocoddyl is built without OpenMP, and a 20-thread machine was sitting idle. This page rebuilds crocoddyl with OpenMP, checks the parallel path gives bit-identical behaviour, and measures what it is worth. The answer is 1.50×, not the 3× the node-level split suggests — because a DDP step has three stages and crocoddyl's OpenMP reaches exactly one of them.

crocoddyl 3.2.1 rebuilt from source with -DBUILD_WITH_MULTITHREADS=ON, Pinocchio 4.1.0, one Intel(R) Core(TM) Ultra 7 265KF (20 threads), commit 726399687. Multithreading reported as on; library actually mapped: /home/humanoid/opt/crocoddyl-omp/lib/libcrocoddyl.so.3.2.1. Step times are means over the 200 control steps of a full 4 s MuJoCo replay. Regenerated from runs/2026-08-13_session16/ by studies/croco_threads_page.py.

The short version. A step is a derivative sweep, a backward pass and a handful of line-search rollouts. Only the derivative sweep is parallel in crocoddyl, and it parallelises well — 8.07 → 2.57 ms, 3.14× on 8 threads. The other two are sequential by construction and no thread count touches them, which caps the whole step at 1.50× however many cores are thrown at it (8% efficiency at 20 threads). That is still the change that finally puts the tail inside the deadline: at the 35-node horizon the controller runs at 101 Hz with a p95 of 15.7 ms against a 20 ms period, where S15 ended at 19.8 ms — i.e. on the deadline rather than under it.

1. Rebuilding without breaking the thing that works

The conda-forge crocoddyl is compiled without CROCODDYL_WITH_MULTITHREADING, so set_nthreads prints a warning and pins the count to 1. There is no conda-forge variant with OpenMP, so the library has to be rebuilt — and the working environment is the one thing that must not be disturbed, because every number in S12–S15 was measured against it.

Three properties of the problem make a safe swap possible, and all three had to be checked rather than hoped:

  • The define does not change the ABI. nthreads_ is an unconditional member of ShootingProblemTpl; CROCODDYL_WITH_MULTITHREADING only gates #pragma omp lines and two assignments. So a rebuilt libcrocoddyl.so is drop-in compatible with the existing Python bindings, and only the library needs building — -DBUILD_PYTHON_INTERFACE=OFF, which is most of the build time.
  • The bindings use RPATH, not RUNPATH. readelf -d on the pywrap shows RPATH $ORIGIN/../../.., and RPATH takes precedence over LD_LIBRARY_PATH — so the obvious selection mechanism silently does nothing. LD_PRELOAD does work, because a preloaded object with the matching SONAME satisfies the NEEDED entry. That makes the choice per-process, explicit on the command line, and reversible by deleting a word.
  • The pinocchio header shim from S15 is needed again. Building crocoddyl 3.2.1 against Pinocchio 4.1.0 hits the same pch.hpp problem as any downstream translation unit, so croco_ext/pinocchio_compat goes on the build's include path too.
One upstream patch was needed, and it is unrelated to threading. core/actions/{lqr,diff-lqr}.hxx initialise a member with cond ? VectorXs::Zero(n) : VectorXs::Ones(n), whose two branches are different Eigen expression types. Newer Eigen rejects it and the build stops on a toy LQR action model this study never instantiates. Both are wrapped in VectorXs(...) to force a common type. It is recorded because a reader reproducing this will hit it and it has nothing to do with OpenMP.
git clone --recursive --depth 1 --branch v3.2.1 https://github.com/loco-3d/crocoddyl
# patch the two LQR ternaries, then:
cmake .. -DCMAKE_BUILD_TYPE=Release \
         -DCMAKE_INSTALL_PREFIX=$HOME/opt/crocoddyl-omp \
         -DCMAKE_PREFIX_PATH=$CONDA_PREFIX \
         -DCMAKE_CXX_FLAGS="-I/studies/croco_ext/pinocchio_compat" \
         -DBUILD_WITH_MULTITHREADS=ON -DBUILD_WITH_NTHREADS=4 \
         -DBUILD_PYTHON_INTERFACE=OFF -DBUILD_TESTING=OFF \
         -DBUILD_BENCHMARK=OFF -DBUILD_EXAMPLES=OFF -DBUILD_WITH_IPOPT=OFF
make -j20 && make install

# and to USE it, per process, changing nothing on disk in the conda env:
LD_PRELOAD=$HOME/opt/crocoddyl-omp/lib/libcrocoddyl.so.3.2.1 python croco_replay.py ...

The check that the swap took: ShootingProblem.nthreads reads back 1 with a warning under the stock library and accepts the value it is given under the preloaded one, and /proc/self/maps names which libcrocoddyl.so the process actually mapped. Every JSON in the run directory records that path, because "which build is this" is not otherwise recoverable from a table of milliseconds.

2. It is the same controller

Parallelising per-node work is only safe if nothing is shared across nodes that is written during calc. Two objects in this study are shared: the passive actuation model (one instance, handed to every node) and the pinocchio model behind the state. Both are read-only in their hot paths — the actuation writes only into its per-node data, and S15's C++ transcription is what makes that true, since a Python actuation in every node would have made the thread count a GIL contention problem instead.

Asserted, then measured. The same replay at 1 and 8 threads:

Identical, not merely close — the trajectory is the same trajectory. test_keepout.py and test_passive.py also pass unchanged under the preloaded library, so the fused keep-out cost and the native actuation are the same functions in the parallel build.

3. One of three stages is parallel

The reason to expect a big win was the S15 accounting: a step is ~45% derivative sweep, ~25% backward pass, ~25% line search, and if the first two thirds of that parallelised the step would fall by 3×. That estimate was wrong, and checking src/core/solvers/ddp.cpp rather than the call graph says why:

solver.calcDiff   -> problem_->calc() + problem_->calcDiff()
                     BOTH carry  #pragma omp parallel for num_threads(nthreads_)

forwardPass       -> for (t = 0; t < T; ++t) m->calc(d, xs_try_[t], us_try_[t]);
                     no pragma, and it CANNOT have one: x_try[t+1] comes from
                     step t's xnext.  It never calls ShootingProblem::calc at all,
                     so nthreads_ is not in its path.

backwardPass      -> Riccati recursion, node t+1 feeds node t.  Sequential.
stage of one step1 thread ms8 threads msspeed-upparallel in crocoddyl?
solver.calcDiff (calc + calcDiff sweep)8.072.573.14×yes
one line-search rollout (SolverDDP::forwardPass)0.990.991.00×no — sequential
backwardPass (Riccati + BoxQP)5.295.390.98×no — sequential

The derivative sweep does what it should — 8.07 → 2.57 ms, 3.14× on 8 threads. The rollout does not move at all (0.99 → 0.99 ms), and the backward pass does not either (5.29 → 5.39 ms). So the sequential floor of a one-iteration step is 6.4 ms — and that counts one rollout, while FDDP's line search takes about four of them per iteration, all on the sequential side of the ledger.

The curve leaves the ideal line immediately and is flat by four threads. That is Amdahl and not overhead: with the derivative sweep at ~41% of a one-thread step, the ceiling is 1/(1 − 0.41) = 1.7×, and the measurement lands at 1.50×. Efficiency falls to 8% at 20 threads, which is the honest way to say that everything past about four cores is buying tenths of a millisecond.

It is worth having anyway, and the reason is the tail rather than the mean. At the 50-node horizon above, the p95 falls from 28.4 ms to 20.4 ms. Repeating the sweep at the 35-node horizon — the configuration S15 settled on — gives 14.5 → 9.9 ms mean (1.46×) and, the number that matters, p95 20.8 → 15.7 ms. That is the difference between a controller that misses roughly one deadline in twenty and one that does not miss any.

6. Where this leaves the loop, and what is left

Across S15 and S16 the step went from 236 ms to 9.9 ms and the p95 from 358 ms to 15.7 ms, against a 20 ms control period. The loop is real-time on the mean and on the tail, on this machine, for this maneuver.

  • More cores will not help. The measured ceiling is 1.50× and it is reached by four threads. Anything further has to come from the sequential two thirds.
  • The line search is the largest remaining sequential item — about four full rollouts per iteration, each one a sequential sweep over the horizon. S15 measured and rejected the obvious fix (truncating the alpha ladder saves no time and destabilises the controller). A cheaper rollout, or a step-acceptance test that does not need one, is the next real lever.
  • The backward pass is a Riccati recursion and is sequential in any DDP. Reducing it means fewer nodes or a smaller state, not more threads.
  • Not the Delassus, still — S14 measured it at 2.3% of a node and it has only got smaller in relative terms since.

7. Reproducing this

OMP=$HOME/opt/crocoddyl-omp/lib/libcrocoddyl.so.3.2.1
R=runs/2026-08-13_session16
C=runs/2026-08-13_session15/croco          # the S15 plan, unchanged

LD_PRELOAD=$OMP python croco_ext/test_keepout.py     # same objective under OpenMP
LD_PRELOAD=$OMP python croco_ext/test_passive.py     # same actuation

LD_PRELOAD=$OMP python croco_speed.py manifest --dir $C --out $R/meta.json
LD_PRELOAD=$OMP python croco_speed.py stage    --dir $C --horizon 50 --threads 8 \
                                               --out $R/stage.json
LD_PRELOAD=$OMP python croco_speed.py threads  --dir $C --horizon 50 --iters 1 \
                                               --out $R/threads.json
LD_PRELOAD=$OMP python croco_speed.py threads  --dir $C --horizon 35 --iters 1 \
                                               --threads 1 2 4 8 12 20 \
                                               --out $R/threads_h35.json

# the videos (headless box: GLFW against the live X display)
MUJOCO_GL=glfw DISPLAY=:1 LD_PRELOAD=$OMP python croco_replay.py --tag s13 --ctrl mpc \
    --mpc-horizon 35 --mpc-iters 1 --mpc-threads 20 --dir $C --video --cam brace

python croco_threads_page.py --dir $R --body ../docs/lean/_body_threads_2026-08-13.html \
                             --out 2026-08-13_mpc_threads.html          # this page

Nothing above changes the default behaviour of the study: without LD_PRELOAD every script loads the conda-forge crocoddyl exactly as before, --mpc-threads defaults to 0 (leave crocoddyl's own default alone), and the S15 numbers reproduce unchanged. The rebuilt library lives outside the conda environment and can be deleted without consequence.
